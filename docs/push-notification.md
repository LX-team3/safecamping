# 알림 기능 정리 (로컬 알림 · Firebase 푸시)

- 정리한 날: 2026-11-24 / 브랜치 `lyh-aibrief`
- 작업 기록의 정본은 `docs/progress.md`. 이 문서는 알림의 흐름, 개념 설명, 설정, 시연 방법, 남은 일을 모은 것이다

## 1. 만들려는 것

**PC 웹에서 캠핑 일정을 등록하면, 같은 회원의 폰에 알림이 오게 한다.**

```
[미리 한 번]  폰 앱에서 A로 로그인     → 서버가 "A의 폰 주소"를 기억
[PC에서]     PC 웹에서 A로 로그인
             캠핑 일정 등록            → 서버가 A의 폰 주소를 찾아 10초 뒤 발송
[폰에서]     잠금화면에 알림           → 누르면 그 일정의 브리핑이 열림
```

이 흐름의 **코드는 모두 있다**(5번까지). 실제 Firebase 발송과 실제 폰에서의 동작은 아직 확인하지 못했다.

## 2. 지금 상태

| 작업 | 쉽게 말하면 | 상태 |
|---|---|---|
| 로컬 알림 (브리핑 · 호우특보 예시) | 폰이 스스로 알림을 띄움 | 코드 완료, 커밋됨(`5d74f2e`) |
| 첫 번째: 폰이 푸시 받기 | 콘솔에서 보낸 알림을 폰이 받고, 누르면 화면이 열림 | 코드 완료, 커밋 안 함 |
| 두 번째(3번): 서버가 보낼 준비 | 콘솔 대신 서버가 보낼 수 있는 기능과 권한 | 코드 완료(서버 테스트 190개 통과), 커밋 안 함 |
| 세 번째(4번): 폰 주소 등록 | 서버가 어느 폰으로 보낼지 앎 | 코드 완료(서버 테스트 200개 · 앱 빌드 통과), 로그인 직후 등록 버그 수정(앱 빌드 통과, 폰 확인 전), 커밋 안 함 |
| 네 번째(5번): 일정 저장 뒤 발송 | PC 예약 → 10초 뒤 폰 알림 | 코드 완료(서버 테스트 208개 · 앱 빌드 통과), 커밋 안 함 |

**확인한 것**
- 서버 전체를 띄우는 테스트에서 진짜 키 파일로 `Firebase 연결 준비됨` 로그가 나왔다
- PC 웹에서 일정을 저장하면 서버의 발송 예약이 실행된다 (로그 `브리핑 푸시 안 보냄: 등록된 폰 없음 (일정 68)`)
- 로그인하지 않은 등록 요청은 401로 막힌다
- 폰(안드로이드 17) 앱이 Firebase 토큰을 받는다. 알림 권한도 허용되어 있다

아직 **확인 못 한 것**: `spring-boot:run` 으로 켰을 때의 로그, 키와 앱이 같은 Firebase 프로젝트인지, 서버에서 Firebase로 실제 발송, 버그를 고친 뒤 실제 폰에서 주소 등록 · 삭제, 알림 받기와 눌러서 이동하기.

(3번 · 4번 · 5번은 처음 계획에서 쓰던 번호다)

## 3. 자주 헷갈리는 것

### 로컬 알림과 Firebase 푸시
로컬 알림은 폰이 스스로 띄우고, Firebase 푸시는 밖에서 보낸 것을 폰이 받는다.

| 하고 싶은 것 | Firebase | 지금 되나 |
|---|---|---|
| 앱에서 버튼을 누르거나 일정을 저장 → 같은 폰에 알림 | 필요 없음 | 코드 있음 |
| PC 웹에서 예약 → 같은 PC에 알림 (탭을 열어 둔 상태) | 필요 없음 | 안 만듦 (브라우저 알림 기능을 써야 함) |
| Firebase 콘솔에서 보냄 → 폰에 알림 | 필요 | 코드 있음 |
| PC 웹에서 예약 → 폰에 알림 | 필요 + 우리 서버 | 코드 있음 (폰 확인 전) |
| 기상청 특보 발효 → 서버가 자동으로 알림 | 필요 + 우리 서버 | 안 만듦 |

Firebase는 배달만 한다. "누구에게, 언제 보낼지"는 우리 서버가 정한다.

### 콘솔로 보내기와 서버로 보내기
```
사람 → Firebase 콘솔 ─┐
                      ├→ Firebase → 폰 앱
우리 서버 ────────────┘
```
Firebase에서 폰으로 가는 길은 같고 **보내는 쪽만** 다르다. 콘솔은 사람이 매번 직접 보내야 해서, 예약에 맞춰 자동으로 보내려면 서버가 필요하다.

### 비슷해 보이는 세 가지

| | `google-services.json` | 기기 토큰 | 서비스 계정 키 |
|---|---|---|---|
| 역할 | 앱이 어느 Firebase 프로젝트인지 알려 줌 | 알림을 받을 폰의 주소 | 알림을 보낼 권한 |
| 쓰는 곳 | 폰 앱 (받기) | 서버가 받는 폰을 고를 때 | 서버 (보내기) |
| 얻는 곳 | Firebase 콘솔에서 Android 앱 추가 | 앱을 켜면 Firebase가 발급 | Firebase 콘솔 › 서비스 계정 |
| 두는 곳 | `client/android/app/` | 서버 메모리 (4번) | **프로젝트 폴더 밖** |
| 민감한가 | 비밀 키는 아님. 그래도 커밋 안 함 | 로그에 남기지 않음 | **매우 민감. 절대 커밋 · 메신저 전송 금지** |

### 토큰은 로그인할 때 만들어지지 않는다
토큰은 폰 앱을 켜면 Firebase가 준다(알림 권한 허용 필요). 로그인은 그 토큰을 **"이 회원의 폰"으로 연결**한다(4번).

| | 토큰 | 로그인의 역할 |
|---|---|---|
| 폰 앱 | 있음 | 이 회원의 **폰이 어디인지** 알려 줌 |
| PC 웹 · 폰 브라우저(크롬 등) | 없음 | **누가 예약했는지** 알려 줌 |

서버는 **같은 계정**이라는 것으로 둘을 연결한다. PC에 토큰이 없어도 되는 이유는 알림을 **받는 쪽이 폰**이기 때문이다. 택배로 치면 PC는 주문하는 사람, 폰은 받는 집이다.

### 폰 주소 등록(4번)은 이렇게 동작한다
4번은 **서버의 주소록에 "이 회원의 폰은 여기"라고 적는 작업**이다. 사용자는 로그인만 하면 되고, 토큰은 앱이 알아서 보낸다.

```
[등록]  폰 앱 실행 → Firebase가 토큰 발급
        폰 앱에서 A로 로그인 → 앱이 서버에 토큰 abc를 보냄
        서버: 로그인 세션을 보니 A → "A = abc" 를 적음
[사용]  PC에서 A가 일정 등록 → 10초 뒤 서버가 A의 토큰 abc를 찾아 발송 (5번)
[삭제]  폰 앱에서 로그아웃 → "A = abc" 를 지움
```

| 폰 앱에서 하는 일 | 서버 주소록 |
|---|---|
| 앱을 켠다 (로그인 전) | 적지 않음 |
| A로 로그인 | `A → abc` 를 적음 |
| 로그인된 채로 앱을 껐다 켬 | `A → abc` 를 다시 적음 |
| 토큰이 바뀜 (앱 재설치 등) | 로그인되어 있으면 새 토큰으로 적음 |
| 로그아웃 | `A → abc` 를 지움 |
| 같은 폰에서 B로 로그인 | A의 연결을 지우고 `B → abc` 를 적음 |
| 다른 폰에서 A로 로그인 | `A → 다른 폰` 으로 바뀜 |

정한 것

| 정한 것 | 이유 |
|---|---|
| 토큰은 **서버 메모리**에 보관 | 토큰을 받는 때(폰 로그인)와 쓰는 때(PC 예약)가 달라 적어 두어야 한다. 시연용이라 DB는 바꾸지 않았다 |
| **회원당 폰 한 대** | 여러 대는 필수가 아니라 이번에는 하지 않았다. 나중에 로그인한 폰만 기억한다 |
| 앱은 **토큰만** 보내고 회원 아이디는 보내지 않음 | 남의 이름으로 내 폰을 등록해 그 사람의 알림을 받지 못하게. 누구인지는 서버가 로그인 세션에서 안다 |
| 로그아웃 **직전**에 삭제 | 로그아웃하면 로그인이 필요한 삭제 API를 부를 수 없다. 삭제에 실패해도 로그아웃은 된다 |
| 등록된 토큰과 **같을 때만** 삭제 | 예전 폰에서 로그아웃해도 지금 폰의 등록은 남게 |
| 우리 코드는 토큰을 콘솔 · 서버 로그에 남기지 않음 | 토큰은 폰의 주소라서. 앱 콘솔에 출력하던 줄도 지웠다. 단, 지금 설치된 앱에서는 **Capacitor가 안드로이드 로그(logcat)에 토큰을 남긴다**. 로그를 공유할 때 토큰을 가린다 |

PC 웹과 폰 브라우저에는 토큰이 없어 로그인해도 아무것도 등록하지 않는다. DB · 로그인 설정 · 라이브러리도 바꾸지 않았다.

### 로그인 직후 등록이 실패하던 버그 (고침)
PC에서 일정을 저장해도 알림이 오지 않고, 서버 로그에 `브리핑 푸시 안 보냄: 등록된 폰 없음` 이 나왔다.

```
[고치기 전]  앱에서 로그인 → 서버가 보안용 쿠키(CSRF)를 지움
             → 앱이 곧바로 토큰을 보냄 → 쿠키가 없어 403 → 등록 안 됨
[고친 뒤]    앱에서 로그인 → 앱이 GET 요청으로 새 쿠키를 받음
             → 토큰을 보냄 → 등록
```

CSRF 쿠키는 다른 사이트가 몰래 보낸 요청을 막는 값이다. 저장 · 삭제 같은 요청은 이 값이 맞아야 통과한다.

| 무엇 | 내용 |
|---|---|
| 앱 로그 | `[푸시] 서버 등록 실패 요청을 처리할 수 없습니다. 새로고침 후 다시 시도해 주세요.` |
| 왜 테스트 화면을 열면 됐나 | `location.href` 가 앱 화면 전체를 새로 불러온다. 이때는 로그인 확인(GET)이 먼저라 쿠키가 있어 등록된다. 테스트 화면 자체가 등록하는 것은 아니다 |
| 고친 곳 | `client/src/utils/pushNotify.js` 의 `registerToken`. 그래도 403이면 한 번만 다시 보낸다 |
| 바꾸지 않은 것 | 서버, 로그인 · 보안 설정, DB |
| 확인한 것 | 쿠키 없이 보내면 같은 403 문구가 나온다. GET 뒤에 보내면 CSRF를 통과한다(로그인하지 않아 401). 앱 빌드 통과 |
| 확인 못 한 것 | 실제 폰에서 로그인 → 등록 → 알림 |

로그인 직후 쿠키가 지워진다는 것은 서버의 로그인 설정을 보고 판단했다.

### 일정 저장 뒤 발송(5번)은 이렇게 동작한다
5번은 **PC에서 일정을 저장하면, 10초 뒤 주소록에서 폰을 찾아 알림을 보내는 작업**이다.

```
① PC 웹에서 A가 새 일정 저장  → 서버가 DB에 저장하고 바로 "저장됨" 응답
② 서버가 10초 뒤에 할 일로 예약  (PC 화면은 기다리지 않음)
③ 10초 뒤: A의 토큰을 찾음      (4번 주소록)
④ Firebase로 발송               (3번)
⑤ 폰 잠금화면에 알림
⑥ 누르면 내 캠핑 화면에서 그 일정의 브리핑이 펼쳐짐
```

| 보내는 것 | 내용 |
|---|---|
| 제목 | `캠핑 브리핑이 도착했어요` |
| 본문 | `○○캠핑장 · 특보 · 날씨 · 준비물을 확인해 보세요` |
| 맞춤 데이터 `path` | `/app/my-camping` (누르면 열 화면) |
| 맞춤 데이터 `brief` | 일정 id (펼칠 브리핑) |

| 어디서 저장하나 | 폰에 오는 알림 |
|---|---|
| PC 웹 · 폰 브라우저 | 10초 뒤 푸시 (`notifyPhone: true` 로 저장) |
| 폰 앱 | 5초 뒤 로컬 알림. 두 번 울리지 않게 푸시는 안 보냄 |
| 기존 일정을 고침 | 없음. **새로 등록할 때만** 보낸다 |

정한 것

| 정한 것 | 이유 |
|---|---|
| 저장 **10초 뒤** 발송 | 저장한 뒤 폰을 잠그고 보여 줄 시간. 발송을 시작하는 시각이라 실제 도착은 조금 늦을 수 있다 |
| 토큰은 **10초 뒤에** 찾음 | 그사이 로그아웃했으면 보내지 않게 |
| 알림에 실패해도 **일정 저장은 성공** | 알림은 부가 기능이라서. 등록된 폰이 없어도 조용히 넘어간다 |
| 10초 안에 일정을 지우거나 고쳐도 **알림은 그대로 감** | 시연용이라 처리하지 않기로 했다. 지운 일정은 눌러도 펼칠 브리핑이 없다 |
| 예약은 **서버 메모리**에만 있음 | 시연용. 10초 안에 서버를 끄면 사라진다 |
| 로그에는 **일정 id만** 남김 | 회원 아이디와 토큰이 남지 않게 |

함께 고친 것
- 폰이 이미 내 캠핑 화면을 띄운 상태면 방금 PC에서 만든 일정이 목록에 없어 브리핑이 안 열렸다 → 목록을 다시 받게 했다
- 지난 일정을 거르던 조건이 동작하지 않았다 → 체크아웃 날짜로 거르게 했다

브리핑 내용은 PC와 다를 수 있다
- 특보와 날씨는 서버에서 받지만, **1분 진단 결과와 체크한 준비물은 폰에 저장된 값**을 쓴다. 시연 전에 폰 앱에서도 진단해 둔다
- 출발이 4일 이상 남은 일정은 특보와 예보 대신 확인 가능한 날짜만 나온다. **3일 안에 출발하는 일정**으로 시연한다

### 서버가 알림을 보내려면 네 가지가 필요하다

| 택배로 치면 | 실제 | 상태 |
|---|---|---|
| 배달하는 방법 | 3번 코드 | 코드 완료 |
| 출입증 | 서비스 계정 키 + 환경변수 | 등록함, 키 파일 읽기는 테스트에서 확인 (실제 발송은 확인 전) |
| 받는 주소 | 4번 (기기 토큰) | 코드 완료, 폰 확인 전 |
| 언제 무엇을 보낼지 | 5번 (일정 저장 10초 뒤) | 코드 완료, 폰 확인 전 |

## 5. 설정

### git에서 받은 뒤 따로 준비할 것
아래 세 가지는 git에 올라가지 않는다. 코드를 받은 뒤 필요한 것만 준비한다.

| | ① `google-services.json` | ② 서비스 계정 키(JSON) | ③ `GOOGLE_APPLICATION_CREDENTIALS` |
|---|---|---|---|
| 역할 | 폰 앱이 알림을 **받게** 함 | 서버가 알림을 **보내게** 함 | 서버에 ②의 위치를 알려 줌 |
| 어디에 | `client/android/app/` | **프로젝트 폴더 밖** | 내 PC의 윈도우 환경변수 |
| 왜 빠지나 | `.gitignore` 에 있음 | 프로젝트 밖에 있음 | 파일이 아님 |
| 없으면 | 토큰을 못 받음 | 서버는 켜지지만 발송 안 함 | ②가 있어도 발송 안 함 |

| 팀원 | 준비할 것 |
|---|---|
| 푸시가 아닌 기능만 작업 | 없음 (푸시만 안 감) |
| 앱을 직접 빌드 | ① |
| 서버로 푸시까지 발송 | ②와 ③ |

- ①과 ②는 **같은 Firebase 프로젝트**의 것이어야 한다
- ②는 메신저로 보내지 않는다. 같은 Firebase 프로젝트에 초대받아 각자 발급받거나, **시연용 서버 PC 한 대에만** 둔다
- ②는 이름에 `firebase-adminsdk` 가 있을 때만 `.gitignore` 가 막는다. **이름을 바꿔 프로젝트 안에 넣으면 git에 올라갈 수 있다**

### 폰 앱 (받기): `google-services.json` 등록
1. https://console.firebase.google.com 에서 프로젝트를 만든다 (이미 있으면 그 프로젝트를 연다. 새로 만들지 않는다)
2. Android 앱을 추가한다 (이미 있으면 건너뛴다). 패키지 이름은 `com.campin.app` (`capacitor.config.json` 의 `appId` 와 같아야 함)
3. `google-services.json` 을 받는다. 나중에 다시 받을 때는 프로젝트 설정 › 일반 › 내 앱에서 받는다
4. `client/android/app/` 에 넣는다. 이름은 정확히 `google-services.json` 이어야 한다 (`google-services (1).json` 처럼 저장됐으면 이름을 고친다)
5. 프로젝트 폴더에서 확인한다. 첫 줄은 `True`, 둘째 줄은 `google-services.json` 경로가 나와야 한다 (둘째 줄은 git에서 제외된다는 뜻)
```powershell
Test-Path client\android\app\google-services.json
git check-ignore client/android/app/google-services.json
```
6. 안드로이드 스튜디오에서 **다시 Run** 해 앱을 설치한다. 파일을 넣기 전에 설치한 앱은 토큰을 받지 못한다
7. 커밋하지 않고, 앱을 빌드할 팀원에게 따로 전달한다

안드로이드 쪽 Gradle 설정은 이미 되어 있다. 파일이 없어도 빌드는 되지만 푸시는 동작하지 않는다.

### 서버 (보내기): 서비스 계정 키와 환경변수 등록
환경변수에는 키의 내용이 아니라 **키 파일의 경로**를 넣는다.

1. Firebase 콘솔 › 프로젝트 설정 › 서비스 계정 › **새 비공개 키 생성**. 앱과 **같은 프로젝트**여야 한다
2. 받은 JSON을 프로젝트 폴더 밖에 둔다. 예: `C:\keys\` (①과 다른 파일이다. 파일 내용을 채팅 · 문서 · 코드에 붙여 넣지 않는다)
3. 환경변수에 **실제 파일 경로**를 등록한다 (아래 `파일이름` 을 바꿔서 한 번만. 아무것도 안 나오면 정상)
```powershell
[Environment]::SetEnvironmentVariable("GOOGLE_APPLICATION_CREDENTIALS", "C:\keys\파일이름.json", "User")
```
4. VS Code 창을 모두 닫았다가 다시 연다 (열려 있던 창은 새 값을 모른다)
5. 새 터미널에서 확인한다. 경로와 `True` 가 나와야 한다
```powershell
echo $env:GOOGLE_APPLICATION_CREDENTIALS
Test-Path $env:GOOGLE_APPLICATION_CREDENTIALS
```
6. 서버를 켜고 로그를 본다

| 로그 | 뜻 |
|---|---|
| `Firebase 연결 준비됨` | 성공 (키 파일을 읽었다는 뜻. 실제 발송은 7장 "PC 예약 알림 확인"에서 본다) |
| `환경변수가 없어…` | 등록이 안 됐거나 VS Code를 다시 켜지 않음 |
| `…NoSuchFileException` | 파일 경로나 이름이 다름 |
| 그 밖의 `키 파일을 쓸 수 없어…` | 다른 JSON을 넣었거나 파일이 깨짐 |
| `Port 8080 was already in use` | 다른 프로그램(예: 도커 컨테이너)이 8080을 쓰는 중. `docker ps` 로 찾아, 꺼도 되는 것인지 확인한 뒤 멈춘다 |

키를 바꾸면 서버를 완전히 껐다 켠다. 유출됐다면 Google Cloud 콘솔 › IAM 및 관리자 › 서비스 계정에서 그 키를 **삭제**하고 새로 받는다(새로 만들기만 해서는 예전 키가 막히지 않는다).

### 선택: 서버를 재시작해도 로그인 유지 (`REMEMBER_ME_KEY`)
푸시에 꼭 필요하지는 않다. 이 값이 없으면 서버를 켤 때마다 임시 키를 써서 "로그인 상태 유지"가 풀린다. 연습하면서 서버를 자주 껐다 켠다면 한 번 등록한다(무작위 값이 만들어지고 화면에는 나오지 않는다).
```powershell
[Environment]::SetEnvironmentVariable("REMEMBER_ME_KEY", [guid]::NewGuid().ToString() + [guid]::NewGuid().ToString(), "User")
```
등록한 뒤 VS Code를 모두 닫았다가 다시 열고, 앱과 PC에서 "로그인 상태 유지"를 켜고 다시 로그인한다. 주소록은 그래도 비워지므로 앱을 완전히 껐다 켠다.

### 푸시와 별개로 git에 없는 설정
`application-local.properties`, `.env` 와 환경변수 `KAKAO_REST_KEY` · `KMA_SERVICE_KEY` · `HRFCO_SERVICE_KEY` · `SAFETY_DATA_KEY` 등도 쓰는 기능에 따라 따로 준비한다. 값은 이 문서에 적지 않는다.

## 6. 폰에 설치하고 실행하기

앱은 PC의 개발 서버(`localhost:5173`) 화면을 불러온다. 시연하는 동안 USB 연결과 아래 터미널을 계속 켜 둔다. 각 터미널은 프로젝트 폴더에서 시작한다.

```powershell
# 터미널 1: 백엔드
cd server; .\mvnw.cmd spring-boot:run

# 터미널 2: 프론트
cd client; npm install; npm run dev

# 터미널 3: 폰을 USB로 연결한 뒤 (USB 디버깅 켜기)
adb reverse tcp:5173 tcp:5173
cd client; npx cap sync android; npx cap open android
```

안드로이드 스튜디오에서 폰을 고르고 Run 을 누른 뒤, 앱이 열리면 알림 권한을 허용한다. USB를 다시 꽂으면 `adb reverse` 도 다시 실행한다.

## 7. 푸시 테스트와 시연

### 토큰 복사
1. PC 크롬에서 `chrome://inspect` 를 열고 `com.campin.app` 의 inspect 를 누른다
2. Console 에 `location.href = '/app/test/notify'` 를 입력한다
3. "등록됨"과 토큰이 보이면 복사한다. 앱을 다시 설치하면 토큰이 바뀔 수 있다

### 폰 주소 등록 확인 (4번)
등록은 앱을 새로 켜거나 로그인할 때 자동으로 된다. 테스트 화면은 **결과를 확인할 때만** 연다. 위의 테스트 화면에 있는 **"서버 등록"** 줄을 본다. 서버를 켜고 폰 앱에서 로그인해 둔다.

| 보이는 문구 | 뜻 |
|---|---|
| `서버에 등록됨` | 성공 |
| `로그인하면 이 폰이 등록돼요` | 로그인이 안 됨 (로그아웃한 뒤에는 이것이 정상) |
| `토큰을 기다리는 중…` | Firebase 토큰을 아직 못 받음. 바로 위 줄의 이유 확인 |
| `서버 등록 실패` | 서버가 꺼졌거나, 로그인이 풀렸거나, 8080이 다른 프로그램이거나, `adb reverse` 가 풀림. "요청을 처리할 수 없습니다"면 앱이 고치기 전 코드인지 확인하고 완전히 껐다 켜기 |

서버를 재시작하면 주소록은 비워지지만 화면에는 "등록됨"이 남아 있을 수 있다. 재시작했다면 앱을 완전히 껐다 켠다(로그인이 풀렸으면 다시 로그인).

### 콘솔에서 보내기
Firebase 콘솔 → Messaging → 새 캠페인 → 알림. 메뉴가 안 보이면 주소 끝을 `/messaging` 으로 바꿔 연다.

| 칸 | 호우경보 | 호우주의보 |
|---|---|---|
| 제목 | `[예시] 인제군 호우경보 발효` | `[예시] 인제군 호우주의보 발효` |
| 맞춤 데이터 `path` | `/app/disaster` | `/app/disaster` |
| 맞춤 데이터 `demo` | `warning` (95mm · 대피) | `advisory` (65mm · 준비) |
| Android 알림 채널 | `push-alert` | `push-alert` |

실제 특보로 오해하지 않도록 제목의 `[예시]` 를 지우지 않는다. "테스트 메시지 전송"에 토큰을 넣고 폰 화면을 잠근 뒤 보낸다.

### PC 예약 알림 확인 (5번)
1. 서버를 **새로 켜고** 로그에서 `Firebase 연결 준비됨` 을 확인한다
2. 프론트를 켜고 `adb reverse tcp:5173 tcp:5173` 을 실행한다
3. 폰 앱을 **완전히 껐다 켠 뒤** 로그인되어 있는지 본다. 풀렸으면 로그인한다 (테스트 화면은 거치지 않아도 된다. 등록됐는지 보고 싶을 때만 연다)
4. 폰 화면을 잠근다
5. PC 웹에서 **같은 계정**으로 로그인해 새 일정을 등록한다 (3일 안에 출발하는 일정)
6. 10초쯤 뒤 알림이 오면 눌러서 브리핑이 펼쳐지는지 본다

알림이 안 오면 서버 로그를 본다.

| 로그 | 뜻 |
|---|---|
| `브리핑 푸시 보냄` | Firebase가 받음. 폰의 인터넷과 알림 설정 확인 |
| `브리핑 푸시 안 보냄: 등록된 폰 없음` | 3번 순서를 다시 하고, PC와 같은 계정인지 확인. 그래도 나오면 테스트 화면의 "서버 등록" 문구를 확인 |
| `브리핑 푸시 보내지 못함` | 바로 위의 `푸시 발송 실패: …` 확인. 이 줄이 없으면 서버가 키를 못 읽은 것 |
| `푸시 발송 실패: SENDER_ID_MISMATCH` | 키와 앱의 Firebase 프로젝트가 다름 |
| `푸시 발송 실패: UNREGISTERED` | 앱을 지웠거나 토큰이 바뀜. 앱을 완전히 껐다 켜기 |
| 아무 로그도 없음 | 새 등록이 아니라 기존 일정을 고쳤거나, 서버가 예전 코드임 |

다시 연습할 때는 같은 캠핑장과 체크인 날짜의 일정을 **지우고** 등록한다(중복 등록이 안 됨).

- [ ] PC 웹에서 새 일정 저장 → 10초쯤 뒤 잠금화면 알림 → 누르면 그 일정의 브리핑이 펼쳐진다 (5번)
- [ ] 폰에 내 캠핑 화면을 띄운 채 잠가도 위와 같이 된다 (5번)
- [ ] 폰에서 로그아웃한 뒤 PC에서 저장하면 알림이 오지 않는다 (5번)
- [ ] 앱에서 일정을 저장하면 알림이 한 번만 온다 (5번)
- [ ] 앱에서 일정 저장 → 5초 뒤 알림 → 누르면 브리핑이 펼쳐진다
- [ ] 테스트 화면의 호우 예시 버튼 → 5초 뒤 알림 → 재난지도 (푸시가 늦을 때의 예비 방법)

### 안 될 때

| 증상 | 확인할 것 |
|---|---|
| 토큰이 안 나옴 | `google-services.json` 위치와 패키지 이름, 앱 재설치 |
| 알림이 안 옴 | 인터넷, 방해금지, 앱 알림 설정, 토큰을 끝까지 복사했는지 |
| 누르면 앱만 열림 | 맞춤 데이터의 `path`. 테스트 전송에 맞춤 데이터가 실리는지는 확인 못 함. 안 실리면 "검토 → 게시"로 보낸다 (설치된 모든 기기로 가고 늦을 수 있음) |
| 흰 화면 | `npm run dev` 와 `adb reverse` (`adb reverse --list` 가 비어 있으면 다시 실행) |

### 발표에서 말할 때
- PC 예약 알림 (폰에서 확인한 뒤): "PC 웹에서 캠핑 일정을 등록하면 서버가 같은 회원의 폰으로 브리핑 알림을 보냅니다. 시연에서는 10초 뒤에 보내지만, 실제 서비스에서는 캠핑 전날 저녁에 보낼 계획입니다."
- 특보 알림: "시연에서는 Firebase 콘솔에서 예시 특보를 직접 보냅니다. 기상청 특보를 받아 서버가 자동으로 발송하는 것은 다음 단계입니다."

## 8. 남은 작업

| 순서 | 할 일 | 누가 |
|---|---|---|
| 1 | `spring-boot:run` 로그에서 `Firebase 연결 준비됨` 확인, 키와 앱이 같은 Firebase 프로젝트인지 확인 | 사람이 직접 |
| 2 | 7장 "PC 예약 알림 확인"과 점검표로 폰 확인 (로그인 직후 등록 버그를 고친 것부터) | 사람이 직접 |
| 3 | 커밋 · 푸시 · PR | 요청할 때 |

4번과 5번 코드는 끝났고, 로그인 직후 등록이 실패하던 버그도 고쳤다(동작과 버그는 3장, 폰 확인은 7장).

PC 예약 알림이 오려면
- 폰에 우리 **앱**이 설치되어 있고 알림을 허용했을 것
- 폰 앱에서 **PC와 같은 계정**으로 로그인해 두었을 것
- 같은 계정으로 **발표용 폰에서 마지막으로** 로그인했을 것 (회원당 한 대만 기억. 이미 로그인되어 있으면 앱을 완전히 껐다 켜기)
- 폰과 서버 PC가 인터넷에 연결되어 있을 것
- 폰 앱 로그인 뒤 서버를 재시작하지 않았을 것 (재시작했다면 앱을 완전히 껐다 켜고, 로그인이 풀렸으면 다시 로그인)
- 환경변수 `REMEMBER_ME_KEY` 가 없으면 서버를 재시작할 때 "로그인 상태 유지"가 풀린다

## 9. 시연용과 실서비스의 차이

| | 시연용 (지금) | 실서비스 |
|---|---|---|
| 발송 시각 | 저장 10초 뒤 | 캠핑 전날 저녁 |
| 토큰 · 발송 예약 보관 | 서버 메모리 (DB 변경 없음) | DB 테이블 |
| 회원당 폰 | 한 대 (나중에 로그인한 폰) | 여러 대 |
| 서버 재시작 | 사라짐. 앱을 완전히 껐다 켜서 등록 | 유지 |
| 일정 삭제 · 변경 | 예약된 알림은 그대로 감 | 발송 취소 · 변경 |
| 기상청 특보 | 콘솔에서 예시를 직접 보냄 | 서버가 자동 발송 |

## 10. 정해야 할 것
- 커밋 안 한 코드(폰 푸시 · 서버 푸시 · 폰 주소 등록 · 일정 저장 뒤 발송 · 등록 버그 수정)를 언제 커밋할지
- 앱으로 돌아올 때마다 자동으로 다시 등록하고, 서버 로그에 "폰 등록됨"을 남길지 (서버를 재시작해도 앱을 열기만 하면 되게. 아직 안 만듦)
- 앱이 안드로이드 로그에 토큰을 남기지 않게 Capacitor 로그 설정을 바꿀지
